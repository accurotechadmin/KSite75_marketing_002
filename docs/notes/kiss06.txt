## 2. Project identity and scope

This is a compact, dependency-free PHP web application that renders and edits a stylized **KISS** sign made from **192 circular lights**. The browser UI is an SVG-based light editor, pattern library, and sequence animator. It uses measured coordinates from a photographed sign rather than a generated grid.

The application is intentionally simple:

- PHP 8.1 or newer
- server-rendered HTML and SVG
- inline CSS
- inline vanilla JavaScript inside an IIFE
- same-origin `fetch()` calls
- JSON files for persistence
- `flock()` for cooperating-process file locking
- no Composer packages
- no npm packages
- no framework
- no build step
- no database
- no sessions or user accounts
- no browser local storage
- no polling, push, or WebSockets
- no external network calls

This is **not** a physical-light controller. It contains no GPIO, DMX, Art-Net, MQTT, serial, USB, MIDI, lighting-console protocol, or device bridge. Unless new code has been added, “lights” means browser-rendered SVG circles and JSON state only.

All visitors share one global live sign state and the same pattern and sequence libraries. There is no per-user state.

## 4. High-level architecture and state ownership

```text
Browser
  ├─ GET index.php
  │    └─ PHP reads dot-layout.json and server-renders 192 SVG circles
  ├─ GET/POST state.php
  │    ├─ reads dot-layout.json for authoritative IDs
  │    └─ locks, reads, repairs, mutates, and rewrites dots.json
  └─ GET/POST library.php
       ├─ reads dot-layout.json for authoritative IDs
       ├─ locks and manages patterns.json
       └─ locks and manages sequences.json
```

Ownership rules:

- `dot-layout.json` is the geometry and ID authority.
- `dots.json`, through `state.php`, is the shared live-state authority.
- `patterns.json`, through `library.php`, is the saved-pattern authority.
- `sequences.json`, through `library.php`, is the saved-sequence authority.
- The unsaved sequence draft exists only in browser memory.
- The blue/cyan dot selection is only browser UI state; it is not persisted.
- Sequence playback is browser-timed with `setTimeout`, but every displayed frame is sent to `state.php` and becomes the shared live state.
- Other visitors do not receive live updates automatically; they see changes on their next load or API operation.

## 5. Geometry contract

`dot-layout.json` is immutable unless the user explicitly requests a geometry change. Never re-grid, normalize, round, reorder, rename, regenerate, or casually edit the coordinates.

Expected top-level schema:

```json
{
  "viewBox": [0, 0, 1152, 524],
  "dotCount": 192,
  "dots": [
    {
      "id": "K-A-R01-C01",
      "letter": "K",
      "section": "K-A",
      "row": 1,
      "column": 1,
      "x": 17.341,
      "y": 17.458,
      "r": 16.5
    }
  ]
}
```

Invariants:

- Exactly 192 entries.
- Every ID is unique and nonempty.
- Array order is authoritative and is reused when normalizing all state maps.
- Every dot has numeric `x`, `y`, and `r`.
- All current radii are 16.5.
- ViewBox is `[0, 0, 1152, 524]`.
- Approximate coordinate extents are x `17.341–1134.301` and y `17.458–506.616`.
- Letter totals: K = 72, I = 36, first S = 42, second S = 42.
- Sections: K-A 36, K-B 18, K-C 18, I-A 36, S1-A 9, S1-B 12, S1-C 21, S2-A 9, S2-B 12, S2-C 21.

Every complete dots or brightness map must contain exactly these 192 IDs. Missing IDs, unknown IDs, invalid types, or reordered persisted maps are repaired or rejected according to context.

## 6. Persisted data models

### 6.1 Live state: `dots.json`, schema version 3

```json
{
  "version": 3,
  "updated_at": null,
  "pattern_name": null,
  "dots": {
    "K-A-R01-C01": false
  },
  "brightness": {
    "K-A-R01-C01": 100
  }
}
```

The real `dots` and `brightness` objects each contain all 192 IDs in layout order.

Rules:

- `dots[id]` must be an exact JSON boolean.
- `brightness[id]` must be an exact JSON integer from 0 through 100.
- On/off and brightness are independent. An off light retains the brightness it should use when turned on later.
- Manual toggles, bulk actions, and brightness edits clear `pattern_name`.
- Importing/loading a named pattern sets `pattern_name` to the sanitized imported name.
- `updated_at` is UTC ISO-8601 from `gmdate('c')` after mutation.
- Malformed/missing stored data is normalized against the 192 authoritative IDs.
- Missing or invalid stored brightness values are repaired to 100.
- Old live-state versions are migrated to version 3 during the next state transaction.

### 6.2 Pattern format, current version 2

```json
{
  "format": "kiss-dot-pattern",
  "version": 2,
  "name": "checker",
  "exported_at": "optional browser timestamp",
  "dot_count": 192,
  "dots": { "...all 192 ids...": true },
  "brightness": { "...all 192 ids...": 75 }
}
```

Compatibility:

- Official pattern version 1 is accepted; brightness defaults to 100.
- Pattern version 2 requires a complete brightness map.
- `state.php` also accepts copied server-state objects from versions 1, 2, or 3.
- A bare complete boolean map is accepted and receives brightness 100.
- A supplied `dot_count` must equal 192.
- Names are optional for imports but required when saving to the server library.
- Names are stripped of ASCII control characters and limited to 80 by PHP byte length, despite UI/documentation often describing this as characters.

Saved pattern records add:

- `id` such as `pat_<16 hex characters>`
- `created_at`
- `updated_at`

The pattern library wrapper remains:

```json
{
  "version": 1,
  "updated_at": null,
  "patterns": []
}
```

### 6.3 Sequence format, current version 2

```json
{
  "format": "kiss-dot-sequence",
  "version": 2,
  "name": "marquee chase",
  "exported_at": "optional browser timestamp",
  "dot_count": 192,
  "default_frame_duration_ms": 500,
  "loop": true,
  "frames": [
    {
      "name": "left",
      "duration_ms": 350,
      "dots": { "...all 192 ids...": true },
      "brightness": { "...all 192 ids...": 100 }
    }
  ]
}
```

Rules:

- 1 through 120 frames for imported/saved sequences.
- Each frame contains complete 192-ID dots and brightness maps.
- Frame duration is an integer from 50 through 60,000 ms.
- `default_frame_duration_ms` follows the same limits.
- `loop` must be boolean.
- Frame and sequence names are optional except that the sequence name is required for server save.
- Version 1 sequences are accepted and receive brightness 100 in every frame.
- Version 2 requires brightness in every frame.

Saved sequence records add `id`, `created_at`, and `updated_at`; IDs use the `seq_` prefix. The sequence wrapper stays version 1 with a `sequences` array.

## 9. Exact dot selection and brightness behavior

This behavior is important and was deliberately added in recent revisions.

### 9.1 Normal click or keyboard activation

- A normal click on a dot toggles that dot through `state.php`.
- Enter or Space on a focused dot performs the same action.
- After the server response completes, that single dot becomes the brightness target and receives the cyan circular selection stroke.

### 9.2 Ctrl/Cmd multi-selection

- Ctrl-click or Command-click adds/removes the clicked dot from the current group.
- Ctrl/Cmd + Enter/Space does the same for keyboard users.
- Group selection does **not** change on/off state.
- Selection order is normalized to authoritative layout order.
- Removing the last selected dot clears the target.

### 9.3 Drag selection

- Pointer drag starts only for the primary left pointer when state is loaded, playback is stopped, and the server is not busy.
- Movement under roughly 6 pixels remains a click.
- Once dragging starts, the code samples the pointer path about every 5 pixels using `document.elementFromPoint()` so quick movement does not skip dots.
- Dragging without Ctrl/Cmd starts a new group.
- Ctrl/Cmd-drag extends the existing group by union.
- Dragging only adds dots; it does not toggle/remove crossed dots.
- Drag selection never changes light on/off state.
- Pointer capture is attempted as an enhancement.
- The post-drag click is suppressed so no dot is toggled accidentally.

### 9.4 Click-away clearing

- Clicking empty space inside the sign clears the selection.
- A document-level click outside the sign clears the cyan selection circles.
- Interacting with the sign itself or any element inside `.brightness-control` preserves the selection.
- Clicking elsewhere in the interface—pattern controls, sequence controls, page background, etc.—clears it.
- This is click behavior; merely tabbing focus elsewhere does not necessarily clear the selection unless the actual code has since changed.

### 9.5 Other actions that establish a brightness target

- All on, All off, and All toggle target all 192 lights.
- All random targets exactly the dots that the completed server response says are on.
- Loading/importing a pattern targets the on dots in the applied result.
- Displaying a sequence frame targets the on dots in that frame.
- The target is client-only and can be cleared without changing server state.

### 9.6 Real-time brightness adjustment

- The slider operates on the frozen current target subset.
- If all target brightness values match, it shows that percentage.
- If target values differ, the output says `Mixed` while the slider sits at the rounded average.
- On every slider `input` event, `previewBrightness()` immediately updates the affected circles and the in-memory `state.brightness` values.
- `scheduleBrightnessUpdate()` coalesces changes at about 120 ms intervals.
- There is at most one active request plus one latest pending update; the code must not build an unbounded request queue.
- All live-state requests still pass through `stateQueue`, preserving same-tab ordering.
- On slider `change`/release, the final value is flushed immediately or immediately after the current request finishes.
- If a server response arrives while a newer brightness value is pending, the pending preview is reapplied to avoid visual snap-back.
- The slider remains usable during brightness coalescing but is disabled during blocking state/library work, playback, no loaded state, or no target.

### API contract

`GET state.php`

- Returns the complete normalized live state.
- May repair/rewrite malformed or old state even on GET.

`POST state.php` accepts:

```json
{"action":"toggle","id":"K-A-R01-C01"}
```

```json
{"action":"all-on"}
{"action":"all-off"}
{"action":"all-toggle"}
{"action":"all-random"}
```

```json
{
  "action":"set-brightness",
  "value":65,
  "ids":["K-A-R01-C01","K-A-R01-C02"]

```

```json
{
  "action":"import-pattern",
  "pattern": {"...complete supported pattern/state object...": true}
}
```

Every successful POST returns the complete updated state, not a delta.

### Transaction behavior

- Supports only GET and POST; others return 405 with `Allow: GET, POST`.
- Request limit is 1 MB.
- Opens `dots.json` with `c+`.
- Acquires `LOCK_EX` for the entire read/normalize/mutate/truncate/write/flush sequence.
- Writes pretty JSON and a final newline.
- Uses in-place `ftruncate` and rewrite, not temporary-file atomic rename.
- Returns cache-disabled JSON.
- Validation errors are 400; configuration/locking/encoding/write failures are 500.

## 13. Concurrency, consistency, and performance model

- Same-tab live mutations are serialized with `stateQueue`.
- Brightness events are locally previewed and coalesced, then serialized through the same queue.
- Server-side `flock()` prevents cooperating PHP processes from simultaneously corrupting a single JSON file.
- Cross-tab and cross-user behavior is still last-writer-wins at the transaction level.
- There is no optimistic version check, ETag, revision number, or conflict UI.
- No polling means browser state can become stale between operations.
- A frame duration of 50 ms can attempt about 20 full-state requests and disk rewrites per second per active player.
- Each frame contains two 192-entry maps, so sequences can become large; imported/saved sequences are capped at 120 frames and 2 MB request size.
- Libraries have no count quota, storage quota, pagination, or cleanup policy.

## 14. Security and operational limitations

Treat these as known architectural risks, not accidental omissions to silently “fix” unless the user requests production hardening:

- No authentication or authorization.
- Any visitor who can reach the endpoints can mutate live state and create/update/delete library records.
- No per-user isolation.
- Writable JSON files are located beside PHP files in the web root and may be directly downloadable depending on server configuration.
- No explicit CSRF token system.
- No rate limiting or abuse throttling.
- No storage quotas.
- In-place truncate-and-rewrite is less crash-durable than temp-file + fsync + atomic rename.
- No audit log.
- No CSP or dedicated security-header layer.
- No database backup or migration mechanism.
- No hardware output layer.

Positive properties to preserve:

- Strict authoritative-ID validation.
- No user-controlled filesystem paths.
- No shell/process execution.
- No dynamic code execution.
- No external dependencies.
- Server output escaping.
- Browser DOM construction largely uses `textContent`, `createElement`, and explicit attributes rather than injecting untrusted HTML.
- JSON response caching is disabled.

## 15. Engineering rules for future modifications

When changing this application:

1. Read the relevant full function and its callers before editing. Because `index.php` is monolithic, side effects often cross UI sections.
2. Preserve the exact 192-ID geometry contract and order unless the user specifically requests geometry changes.
3. Keep server-side validation authoritative. Client validation is UX only.
4. Every live mutation must return and apply a complete server state.
5. Keep ordinary state writes and brightness writes serialized through `stateQueue`.
6. Do not regress the brightness system into sending a request for every raw pointer event. Preserve immediate visual preview, approximately 120 ms coalescing, one in-flight update, one latest pending update, and final-value flushing.
7. Preserve multi-selection semantics and click-away clearing unless explicitly changing them.
8. Preserve keyboard access, `aria-pressed`, live status, circular focus indication, and descriptive labels.
9. Never reintroduce the square focus/tap box around SVG dots.
10. Treat blue/cyan selection as client-only; do not persist it unless explicitly requested.
11. Keep pattern and sequence backward compatibility unless a migration plan is requested.
12. Keep file-size, frame-count, duration, name, ID, and brightness limits synchronized between frontend and backend.
13. New server mutations must hold the appropriate lock for the whole transaction and update timestamps.
14. Manual live edits should clear `pattern_name`; intentional named pattern application should set it.
15. Avoid `innerHTML` with user-controlled content. Prefer DOM APIs and `textContent`.
16. Do not add third-party dependencies, frameworks, or hardware integrations without explicit approval.
17. Do not modify real persisted data during tests without backing it up and restoring it.
